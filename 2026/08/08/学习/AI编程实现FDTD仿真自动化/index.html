让 AI 替你跑 FDTD 仿真：编程 Agent 全自动设计优化实战

引言

跑 FDTD 仿真这件事，做光子学的同学应该都不陌生：打开 Lumerical，手动画结构、加光源、放监视器、设置网格精度，跑一次，看结果，不理想就改参数再来一次。如果还要做参数扫描或设计优化，经常是盯着进度条熬到深夜。

最近”找寻归宿的流浪猫”分享了一篇文章和配套视频，用编程 Agent（Vibe Coding）跑通了 Lumerical FDTD、Ansys HFSS、CST 等仿真软件的全自动建模与优化。作者的原话是：

学会了这个方法之后，我再也没有手动跑过仿真了。

参考这两份资料，我把这套方法整理成一篇实战教程：从 Vibe Coding 是什么讲起，到用 Codex 全自动完成一个 1×2 MMI 分束器的设计与仿真，重点是给出可以直接复制的 Prompt，照着改参数就能用。

什么是 Vibe Coding

Vibe Coding 的核心是用自然语言描述意图，让 AI 把代码写出来。但最前沿的玩法已经不止是”聊聊天生成几行代码”，而是：

用自然语言描述目标，让 Agent 负责拆解、执行、调试和交付，人类负责定义问题、设置边界、审核结果。

从工具形态上看，大致分三档：

层次 工具 特点
网页对话 ChatGPT、DeepSeek 等网页端 门槛最低，靠复制粘贴搬运信息，效率也最低
IDE 内 AI VS Code 插件、Trae、AntiGravity、Cursor 能自动补全、修改代码，但还不能独立跑完整流程
纯 Agent 编程 Claude Code、Codex 能调用终端、读写文件、运行脚本、看报错、反复迭代，全流程自动化

纯 Agent 编程的代表工具是 Claude Code 和 Codex。Claude Code 基本只能官方订阅，价格较高；Codex 可以自己注册账号，用相对便宜的价格订阅。第二档的 Cursor、Trae 国际版、Kimi Code、智谱 ZCode 等也可以用，但一些较弱的模型容易出错。本文以 Codex Windows 桌面端为例演示。

为什么 FDTD 场景特别适合交给 Agent

并不是所有工作都适合直接交给 Agent，但 Lumerical 仿真是一个典型的好场景，原因有四个：

原因 说明
任务目标清晰 要仿什么器件、什么波段、什么工艺平台，物理上定义得很明确
反馈链条完整 脚本报错、仿真结果、监视器数据都是机器可读的，Agent 可以自己读结果、自己 debug
验收条件可量化 损耗、透射率、分束比都有明确数值，可以直接写进验收标准
交付物可检查 仿真文件、报告、图都可以打开验证，结果可追溯

换句话说，这个流程天然就是”写代码 → 跑仿真 → 看报错 → 改代码”的闭环，而这正好是编程 Agent 最擅长的循环。所以只要把需求描述清楚，整个迭代就可以完全交给它。

实战：Codex 全自动完成 1×2 MMI 分束器设计

下面用 Lumerical FDTD（2025 R1 版本）演示一个完整案例：设计一个 3D 的 1×2 MMI 分束器，在 1550nm 波段实现等功率分束。全程不需要手动操作 Lumerical。

第一步：准备环境

  1. 在你喜欢的地方创建一个工作文件夹；
  2. 打开 Codex，选择这个文件夹作为 Workspace；
  3. 建议在权限设置里开启”完全访问权限”，这样 Agent 运行脚本、读写文件时不需要一次次手动确认。目前看仿真 Lumerical 并没有太大安全风险，但如果介意，也可以保留手动确认。

第二步：设计 Prompt（最核心的一步）

Prompt 是这套方法里最关键的部分，写得好不好直接决定 Agent 能不能完成任务。一份合格的仿真 Prompt 至少要包含四个要素：

要素 内容
① 解释器路径 Lumerical 自带 Python 解释器的完整路径，让 Agent 知道用什么环境跑脚本
② 器件与工艺参数 结构组成、材料、工艺平台、波段、模式、网格精度等，越详细越好
③ 可量化验收条件 比如”损耗 < 0.5dB、分束不均衡度 < 5%”，让 Agent 知道什么时候算完成
④ 交付物要求 保存 .fsp 文件、生成仿真报告等，方便你事后验收

三个写 Prompt 的小技巧：

  • 解释器路径怎么找：一般和上面类似，都在安装目录下；找不到就用 Everything 搜 python.exe，定位到 Lumerical 目录里的那个。一定要把这个路径提供给 Agent。
  • 验收条件要可量化、且确定能设计出来：别写”性能要好”这种模糊要求。同时心里要有数，这个指标在物理上是能达成的；如果把握不准，可以加一句”如果达不到，请在迭代 X 次后结束”，X 根据场景设成十几次或几十次。
  • 把常见坑写进 Prompt：比如固定文件名自动保存避免弹窗、监视器不要和波导重叠。这些都是实践中 Agent 容易犯的 Lumerical 仿真错误，提醒一次可以省下大量无效迭代，而且可以固化在以后所有的 Lumerical 仿真 Prompt 里复用。

第三步：等待 Agent 自动迭代

把 Prompt 发给 Codex 之后，它会自动完成整个循环：

整个过程不需要人盯着。原作者的演示中大约半小时，Codex 就自动完成了所有仿真、优化和报告生成，并在工作目录下创建好了文件。如果没有开启完全访问权限，中间可能需要手动确认一些操作。

第四步：验收

仿真结束后，验收同样重要：

  1. 打开生成的 .fsp 文件，检查模型结构是否合理；
  2. 查看仿真报告中的器件结构图、光场传输图、损耗和分束功率；
  3. 核对是否满足验收条件（分束不均衡度 < 5%、传输损耗 < 0.5dB）；
  4. 不满足就补充反馈，让它继续迭代。

进阶玩法

这套方法不止能做参数优化：

  • 论文复现：直接喂一篇文献，让 Agent 复现其中的某个结构。只要 Prompt 认真写，就可以一键复现论文里的仿真。
  • MCP 直接控制：更进一步，可以用 MCP 把 Lumerical 直接暴露给 AI 客户端。社区里已经有 lumerical-fdtd-mcp 这样的开源项目，可以在 Codex 里通过工具调用直接控制 Lumerical 会话、运行脚本、读取变量，实现自然语言驱动的仿真工作流。
  • 了解底层 API：如果想弄清 Agent 实际在操作什么，可以看 Lumerical Python API 官方文档。Lumerical 提供了完整的 Python 会话和对象接口（如 lumapi.FDTD()），这正是自动化仿真的基础。

注意事项与边界

  1. 选对工具：较弱的模型很容易在复杂仿真任务中出错，建议优先使用 Claude Code、Codex，或性能足够强的模型。
  2. 物理正确性仍要人核验：Agent 能把脚本跑通、指标达标，但边界条件、材料模型、监视器设置是否物理正确，最终还是要自己检查。AI 节省的是重复劳动，不是思考本身。
  3. 权限风险：开启完全访问权限后，Agent 可以执行任意命令，注意工作环境里不要放敏感数据。
  4. 迭代要有上限：给验收条件设定迭代次数上限，避免在达不到的目标上无限空转。

总结

整套流程概括起来就是四步：

步骤 做什么
1. 准备环境 建工作文件夹，打开 Codex 并设为 Workspace
2. 编写 Prompt 包含解释器路径、器件参数、量化验收条件、交付物要求
3. 自动执行 Agent 自己建模、仿真、debug、优化，循环直到达标
4. 验收结果 检查 .fsp 和报告，不达标就补充反馈继续迭代

一句话：你负责定义问题和验收标准，Agent 负责中间所有的脏活累活。

“工具从来不是为了取代思考，而是为了把思考者从重复劳动中解放出来。当年 MATLAB 替我们算矩阵，FDTD 替我们解麦克斯韦方程，今天 Agent 开始替我们操作这些求解器本身。”
